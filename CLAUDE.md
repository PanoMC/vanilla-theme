# CLAUDE.md

This file gives Claude Code context for working in this repository.

## What this is

`vanilla-theme` is Pano's **reference theme** — but since the theme-core migration it is a
**thin packaging shell**: all logic, plugin infrastructure, page implementations and default
markup live in **`@panomc/theme-core`**, consumed from the `theme-core/` **git submodule**
(the PanoMC/sdk repo, which houses both `packages/theme-core` and `packages/sdk`). This repo
carries only identity (manifest, screenshots), the token/style layer, and generated glue.

**vanilla is NOT a template.** New themes are scaffolded with `bunx theme-core new <name>`;
its manifest id `vanilla-theme` is reserved for the SYSTEM theme. Developing "vanilla's look"
mostly means editing `theme-core/packages/theme-core/src/lib/views/` — the default views ARE
vanilla's appearance, and every other theme inherits them as fallbacks.

## Layout — who owns what

```
manifest.json  theme.config.js       ✍ identity + (empty) view registry
src/styles/tokens.scss  style.scss   ✍ design tokens + vanilla's own CSS
lang-overrides/                      ✍ changed i18n keys only (empty here)
theme-core/                          📦 submodule → PanoMC/sdk (engine + sdk packages)
src/routes/  src/lib/  lang/         ⚙ GENERATED by `theme-core sync` — never hand-edit
src/hooks.*.js  *.config.js          🏭 two-line factory calls into the engine
plugins/  static/runtime  static/lib ⚙ runtime/build artifacts
```

## Commands

```bash
git submodule update --init                    # once after clone
bun install                                    # hangs at "Resolving"? → --backend=copyfile
bun node_modules/@panomc/theme-core/bin/sync.js    # regenerate routes/lib/lang
bun run dev                                    # Vite dev on 3000 (backend via VITE_API_URL)
bun node_modules/@panomc/theme-core/bin/check.js   # contract lint
bun run build                                  # prebuild → vite → fingerprint (reproducible)
```

**Live engine development:** bun copies `file:` deps, so to see engine edits without
reinstalling, symlink them once:
`rm -rf node_modules/@panomc/{theme-core,sdk} && ln -s ../../theme-core/packages/theme-core node_modules/@panomc/theme-core && ln -s ../../theme-core/packages/sdk node_modules/@panomc/sdk`
(dev servers pick up view edits live — the registry cache is dev-disabled).

**Engine updates:** `git -C theme-core pull && git add theme-core` (submodule bump commit),
then sync + build. Until `@panomc/theme-core` is on npm this submodule is the only source;
after publish the `file:` deps may become registry versions.

## Contract (enforced by `theme-core check`, machine-readable in skin-contract.json)

- svelte pinned EXACTLY to the engine's version (plugins share the host runtime)
- plugin view-slot ids, Hook names, lifecycle event names — engine-owned, one mount per hook
- i18n: `lang/` is generated (engine base ⊕ `lang-overrides/`, additive)
- premium license: gate lives in the engine's hooks factory; skipped under `vite dev`,
  enforced in production builds; the zip sha256 is the license identity (builds are
  byte-reproducible — `kit.version.name` is pinned)

## Fork family

`blaze`/`blocky`/`frost`/`banana`-theme are sibling themes on the same engine — they are no
longer synced by patch-porting. Shared behavior arrives via engine version bumps; each fork
carries only `theme.config.js` (view overrides + settingsSchema), `src/views/`, tokens and
lang-overrides. See `theme-core/docs/THEME-AUTHOR-GUIDE.md` and `MIGRATION.md`.
